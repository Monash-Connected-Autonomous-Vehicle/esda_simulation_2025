# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A **colcon workspace** for an IGVC-style autonomous ground vehicle (ESDA 2025), targeting **Ubuntu 22.04 / ROS 2 Humble / Gazebo (gz-sim) / Nav2**. The repo root *is* the workspace root — `build/`, `install/`, `log/` are generated here and gitignored.

Two packages live under `src/`:

| Package | Type | Contents |
|---|---|---|
| `esda_simulation_2025` | `ament_cmake` | Everything: URDF/xacro, Gazebo worlds, launch files, Nav2/SLAM configs, all Python nodes, custom `.msg` interfaces |
| `esda_hardware_2025` | `ament_cmake` (C++) | `ros2_control` `SystemInterface` plugin (`esda_hardware_2025/EsdaHardware2025`) that talks to an STM over serial for the real robot |

Note: this checkout may be on Windows, but the code only builds and runs on Linux/ROS 2. Do not attempt `colcon build` unless the environment is actually Ubuntu.

## Build & run

```bash
colcon build --symlink-install
source install/setup.bash
```

```bash
colcon build --packages-select esda_simulation_2025
```

There are **no tests**. `BUILD_TESTING` only wires up `ament_lint_auto`; `colcon test` runs linters, nothing else.

**The GUI launcher is the intended entrypoint** — it wraps every launch step in `xterm` windows and manages process lifetimes:

```bash
python3 src/esda_simulation_2025/scripts/ui_launch.py
```

`ui_launch_real_robot.py` is the hardware equivalent. Both shell out to `ros2 launch` / `ros2 run`, so their bodies are the authoritative reference for correct launch arguments.

Manual sequence (sim): `launch_sim.launch.py` → SLAM (`online_async_launch.py`) *or* AMCL (`localization_launch.py`) → `navigation_launch.py` → `rviz2 -d src/esda_simulation_2025/config/view_bot.rviz`. See `src/esda_simulation_2025/TO RUN.txt` for the exact argument sets, and `src/esda_simulation_2025/README.md` for the full manual (the root `README.md` is a stale short version — prefer the package one).

Stale Gazebo state is the most common failure (`failed to load joint_state_broadcaster` etc.). Fix: `pkill -f ign && pkill -f gz`, and clear `/dev/shm/fastrtps_*`.

## Adding a Python node — two required steps

Python nodes are **not** an `ament_python` package. They are plain scripts installed by `install(PROGRAMS ...)` in `src/esda_simulation_2025/CMakeLists.txt`.

1. Add the script path to that `install(PROGRAMS ...)` block, or `ros2 run esda_simulation_2025 <script>.py` will not find it.
2. Keep the `#!/usr/bin/env python3` shebang and the `.py` extension — the extension is part of the executable name.

Custom messages are generated by `rosidl_generate_interfaces` in the **same** package, so `from esda_simulation_2025.msg import NavigationRecommendation, LaneParameters` only resolves after a build + source. Editing `msg/*.msg` requires a rebuild before any node importing it will start.

## Architecture: two parallel navigation stacks

The repo contains **two independent ways to drive the robot**. Both publish `/cmd_vel` and must not be run at once.

### 1. Nav2 waypoint navigation (`scripts/waypoint_navigator*.py`)

Uses `nav2_simple_commander` / the `NavigateToPose` action. `waypoint_navigator_recommendation.py` (~2300 lines) is the active revamp: rather than following fixed GPS waypoints, it *synthesises* the next goal each cycle from the local costmap, `/lane_markers`, `/scan` and the global costmap — `update_forward_goal` → `calculate_lane_goal` / `bias_waypoint_toward_free_space` → `send_goal`, with a recovery ladder (`robot_recovery`, `find_left_recovery_goal`, `find_front_recovery_goal`, `retry_recovery_goal`, `no_candidate_found_recovery_waypoint`) and a `/travel_history` costmap layer to discourage revisiting. `waypoint_navigator.py` is the older fixed-waypoint version reading `waypoints/igvc_waypoints.yaml`.

Nav2 behaviour is configured by `config/nav2_params.yaml` (MPPI controller, NavFn/A* planner, `robot_radius: 0.45`) and the custom BT in `behaviour_tree/navigate_recovery.xml`.

### 2. Reactive lane/gap stack (`follow_the_gap.py` + `track_follower.py` + `behaviour_tree.py`)

A hand-rolled arbitration layer that bypasses Nav2:

- `follow_the_gap.py` — disparity-extender gap following from `/scan`, for close obstacles.
- `track_follower.py` — lane-centreline following; also publishes `LaneParameters` on `/lane_parameters`.
- Both publish a `NavigationRecommendation` (`/follow_the_gap_recommendation`, `/track_follower_recommendation`) carrying `source`, `reason`, per-strategy weightings, `confidence`, and a candidate `linear_x`/`angular_z`.
- `behaviour_tree.py` subscribes to both, picks a `NavigationState` (CENTRELINE_FOLLOWING / FOLLOW_THE_GAP / GOAL_NAVIGATION / RECOVERY), and is the only one of the three that should own `/cmd_vel`.

`msg/NavigationRecommendation.msg` is the contract between these nodes — its `reason` enum (lane-pair geometry cases, `RECOVERY_REQUIRED`, …) is where new decision states get added first. `track_follower.py` and `follow_the_gap.py` each have an `enable_cmd_vel` / `test_*_itself` parameter so they can be run standalone without fighting the behaviour tree.

## Perception: lane detection and scan fusion

Three interchangeable detectors, all subclassing the base node in `lane_detection.py`:

- `lane_detection.py` — classic CV (grayscale threshold → Canny → Hough).
- `lane_detection_FCN.py` — FCN segmentation.
- `lane_detection_twinlite.py` — TwinLiteNet+ multi-task model (external repo, gitignored; see `LANE_DETECTION.md` for setup).

Subclasses override only mask/line extraction and visualisation. **All downstream behaviour lives in the base class** — 3D projection via the depth image, `/lane_markers` (MarkerArray), `/lane_obstacles` (PointCloud2), and the `scan_callback` that injects lane points into the LiDAR scan and republishes it as `/scan_fused`.

That fusion is load-bearing: `nav2_params.yaml` costmaps and AMCL subscribe to **`/scan_fused`, not `/scan`**. If lane detection is not running, nothing publishes `/scan_fused` and Nav2 sees no obstacles — hence the UI's "Enable Lane Detection" toggle, which swaps the `scan_topic:=` argument between `/scan` and `/scan_fused`.

## Topic and frame conventions

| Topic | Produced by | Consumed by |
|---|---|---|
| `/scan` | gz bridge (sim) / `velodyne_laserscan` (real) | lane detection, FTG, track follower |
| `/scan_fused` | lane detection base class | Nav2 costmaps, AMCL, SLAM |
| `/lane_obstacles`, `/lane_markers` | lane detection | costmap voxel layer, RViz, waypoint navigator |
| `/travel_history` | `waypoint_navigator_recommendation.py` | global costmap obstacle layer |
| `/lane_parameters` | `track_follower.py` | `behaviour_tree.py` |
| `/cmd_vel` | Nav2 / behaviour tree / teleop | gz bridge → diff drive |

TF: `map → odom` (AMCL or SLAM) → `base_link` (diff drive controller / EKF) → sensor frames from the URDF. Gazebo emits sensor frames prefixed `my_robot_1/...`; `launch_sim.launch.py` patches the camera with a static transform (`camera_link → my_robot_1/base_link/camera`), and SLAM/AMCL must be told `base_frame:=my_robot_1/base_link odom_frame:=my_robot_1/odom` when launched by hand — the UI does this for you.

`/cmd_vel` routing differs between sim and hardware: in sim the gz bridge consumes `/cmd_vel` directly; on the real robot, teleop/Nav2 must be remapped to `/diff_drive_base_controller/cmd_vel_unstamped`.

## Launch file map

| File | Purpose |
|---|---|
| `launch_sim.launch.py` | Gazebo + spawn + `ros_gz_bridge` + controller spawners + EKF. Args: `use_lidar`, `world_file`, `spawn_x/y` |
| `launch_robot.launch.py` | Real robot: `ros2_control_node` + Velodyne + joystick teleop |
| `rsp.launch.py` | robot_state_publisher only (xacro → `robot_description`) |
| `online_async_launch.py` | slam_toolbox mapping |
| `localization_launch.py` | AMCL + map_server |
| `navigation_launch.py` | Nav2 servers from `nav2_params.yaml` |
| `hil_test_launch.launch.py` | Hardware-in-the-loop: URDF + controllers, no Gazebo, no LiDAR |
| `robot_localization_ekf.launch.py` | `robot_localization` EKF from `config/ekf.yaml` |

## Known rough edges

- `loop_waypoints.launch.py` references an executable `algolism.py` that does not exist in `scripts/`.
- `scripts/mission_supervisor.py` is empty; `scripts/slam_manager.py` is a stub.
- Several scripts carry commented-out `from build.esda_simulation_2025.rosidl_generator_py...` imports — leftovers; the real import is `from esda_simulation_2025.msg import ...`.
- `src/.vscode/settings.json` hardcodes another developer's absolute path.
- Stray `frames_*.gv` / `.pdf` TF dumps and duplicated maps (`my_map_save.*`) are committed at the repo root.
